| 2026-11-10 | API: POST, GET one, GET list; no update/delete; no auth until Slice 5 (default; no preference) | Smallest useful surface | Add update/delete |
| 2026-11-10 | Suggested class is computed each time a request is read (not stored on HandlingUnit) in Slice 1; Slice 2 computes the class fresh at quote creation and snapshots it on the quote; a re-quote after expiry recomputes it | Graham's reasoning: quotes expire and a business will not honor an old price once rates or rules have changed, so a new order must be re-quoted today with today's rules. The quote is the immutable record of what was offered (an expired quote cannot be booked); a request is an input, so its class may differ from a later quote's class without inconsistency. Storing the class on the HandlingUnit would add a column that can go stale, and nothing needs it. Rejected idea: a quote copying a stored class from an old request, which would pin a re-quote to outdated rules. Trade-off accepted: an old request fetched after a class-table change may show a different class than it did when submitted | Store suggested_class on HandlingUnit at creation and never recalculate |
| 2026-11-10 | Class table module exposes `CLASS_TABLE_VERSION = "NMFTA-2025-1"`; Slice 2 quotes record the version used, and a booking is rejected if the quote's version differs from the current one | Graham's requirement: quotes are kept as history of what was offered, but every quote that becomes a transaction must use the most up-to-date class table. Expiry alone does not guarantee this, because the table could change inside a quote's validity window. Slice 1 only adds the constant; storage and the booking check belong to Slice 2 (see slices/slice_02_notes.md) | Rely on quote expiry alone |
| 2026-11-11 | Weight, dimensions and quantity must be positive whole numbers (inches, pounds); fractional values are rejected | Carriers measure LTL freight in whole inches and round fractions up (shipper guidance and parcel carrier rules; no LTL tariff text or official NMFC rule was found, ClassIT+ is paywalled). Whole-number inputs keep the density math exact and match the hand-worked examples; shippers round up before submitting | Accept decimals and round each dimension up to the next whole inch before computing density |
| 2026-11-11 | A user-supplied freight class must be one of the 18 standard NMFC classes (50 to 500, including 77.5, 92.5, 110, 150, 200, 500); the 13-tier density table is used only for suggestions | Catches typos and invalid values before they reach pricing. Validating against the 13 density-tier classes would wrongly reject legitimate fixed-commodity classes. The list of 18 is consistent across several broker and carrier sources (GlobalTranz, WWEX, PCB, ParcelPath); an NMFTA primary source was not checked. The check does not confirm the class is right for the commodity | Accept free text; validate against only the 13 density classes |
| 2026-11-11 | NMFC code (optional) gets a light format check: 4 to 6 digits, optional hyphen and 1- or 2-digit sub-number; whitespace trimmed; no existence or commodity check | Graham's goal: keep obviously ridiculous strings off the bill of lading. Format checked against NMFTA's data-file layout (6-digit item number plus 2-digit sub) and a shipper guide (4 to 6 digit items, 2-digit sub joined by a hyphen). Pattern is deliberately lenient (4 to 6 digits, 1 or 2 digit sub) so real codes are not rejected; it cannot confirm the code exists, which needs the paid NMFC database | Accept any short string; strict 6-digit pattern |
| 2026-11-11 | API returns density as a JSON string rounded to 2 decimals (for example "9.60"), not a JSON number | Exact decimals stay exact for clients (floats cannot hold values like 4500/91 exactly); matches DRF's default for Decimal fields and the project's Decimal-everywhere rule; Slice 2 prices can follow the same pattern. Class is still chosen from the unrounded density | JSON number (would need overriding DRF's default; client sees a float) |
| 2026-11-11 | Addresses are flat fields on QuoteRequest (origin_* and destination_*: street, city, state, postal code) with shared validators, not a separate Address model | No address is reused or edited in Slice 1, so a separate model adds tables and nested serializers for no benefit yet. Flat fields copy the address into each request, so history cannot change (consistent with immutable quotes). Shared validators write the state/ZIP rules once. A SavedAddress model can be added later as a purely additive change, copying values into requests (copy-on-save); QuoteRequest need not link to it | Separate Address model linked from QuoteRequest; flat fields with duplicated validation |
| 2026-11-11 | List endpoint is paginated (DRF page-number pagination, newest first with id tiebreaker; page size proposed in plan, suggestion 20) | Bounded response size with nested handling units; standard API practice; cheap to add now, whereas adding pagination later changes the list from an array to an object and breaks clients | Unpaginated list |
